# Security Fix #1 — Redis TLS, TF-managed Encryption Key, SG Descriptions + Hardening

**Implementation Date**: 2026-05-07
**Status**: ✅ Completed
**Version**: 1.0
**Branch**: `chore/security-ci`
**Pull Request**: #7 — *ci: add gitleaks + trivy scans, fix flagged real issues*

## Overview

This PR is the first security pass on the `cloud/aws/` Terraform stack. The driver was a new CI job (`.github/workflows/security.yml`) that runs `gitleaks 8.30.1` plus `trivy` on every push/PR. That scan produced a batch of legitimate AWS-resource findings; the same branch fixes the genuine ones and suppresses the rest with rationale-bearing inline `tfsec:ignore` / `trivy:ignore` comments so future maintainers can audit *why* a finding is suppressed without re-reading the whole PR.

Three headline behavioural changes:

1. **Redis is now TLS-only** — clients must connect via `rediss://`.
2. **`enterprise.passwordEncryptionKey` is now generated by Terraform** (`random_bytes`) and persisted in TF state, not regenerated on every helm regen.
3. **Every security group and SG rule carries a `description`**, satisfying tfsec `aws-ec2-add-description-to-security-group(-rule)`.

Additional hardening (KMS envelope encryption for EKS secrets, IMDSv2 enforcement, public-IP-on-launch off, control-plane logging, etc.) lands in the same PR and is documented in §6.

This repo is greenfield-only (deploys land on empty AWS accounts), so no in-place migration is provided. Compliance-side notes for fresh deploys live in `DOC:SECURITY_NOTES.md`.

## Files Modified / Created

### 1. NEW: `tf/secrets.tf`

```hcl
resource "random_bytes" "password_encryption_key" {
  length = 32
}
```

AES-256 key (32 bytes, base64) for Dify Enterprise password-policy encryption (chart key: `enterprise.passwordEncryptionKey`; DB: `enterprise.sys_settings.PASSWORD_POLICY`). Generated once and persisted in TF state, so the key is stable across `terraform apply` re-runs and across re-runs of `scripts/4_generate_dify_helm.sh`. **Rotating it invalidates any password-policy ciphertext already stored in the database.**

### 2. MODIFIED: `tf/providers.tf`

Added `hashicorp/random ~> 3.6` to `required_providers` (consumed by `tf/secrets.tf`).

### 3. MODIFIED: `tf/outputs.tf`

```hcl
output "password_encryption_key" {
  description = "AES-256 base64 key for enterprise.passwordEncryptionKey..."
  value       = random_bytes.password_encryption_key.base64
  sensitive   = true
}
```

Exposes the key to the script layer (`scripts/3_post_tf_apply.sh` reads it via `terraform output -raw`).

### 4. MODIFIED: `tf/elasticache.tf` — Redis TLS + at-rest encryption

```hcl
# Encryption at rest and in transit. Clients must connect via TLS (rediss://), so the
# generated Helm values set externalRedis.useSSL: true.
at_rest_encryption_enabled = true
transit_encryption_enabled = true
```

The Redis security group (`aws_security_group.redis`) gained:
- A top-level `description` (`"Security group for dify-${var.deployment_id} ElastiCache Redis"`).
- Per-rule descriptions on the 6379-from-EKS ingress and the wide-open egress.
- A `tfsec:ignore:aws-ec2-no-public-egress-sgr` annotation explaining why egress is intentionally `0.0.0.0/0` (NAT-routed AWS API access for snapshots/KMS/CW logs).

### 5. MODIFIED: `tf/eks.tf` — KMS envelope encryption, control-plane logging, IMDSv2, SG descriptions

Three categories of change:

#### a) KMS envelope encryption for Kubernetes secrets

```hcl
resource "aws_kms_key" "eks_secrets" {
  description             = "Envelope encryption key for ${local.cluster_name} Kubernetes secrets"
  enable_key_rotation     = true
  deletion_window_in_days = 7
  ...
}
resource "aws_kms_alias" "eks_secrets" {
  name          = "alias/${local.cluster_name}-secrets"
  target_key_id = aws_kms_key.eks_secrets.key_id
}
```

Wired into the cluster:

```hcl
encryption_config {
  provider { key_arn = aws_kms_key.eks_secrets.arn }
  resources = ["secrets"]
}
```

#### b) Control-plane logging

```hcl
enabled_cluster_log_types = ["api", "audit", "authenticator", "controllerManager", "scheduler"]
```

#### c) IMDSv2 on worker nodes

```hcl
metadata_options {
  http_endpoint               = "enabled"
  http_tokens                 = "required"
  http_put_response_hop_limit = 2
}
```

Hop limit 2 lets pods reach IMDS through one extra network hop while still rejecting unauthenticated v1 requests.

#### d) Cluster-level `tfsec:ignore`s

- `aws-eks-no-public-cluster-access` — public endpoint is gated on `elb_mode == "internet-facing"`.
- `aws-eks-no-public-cluster-access-to-cidr` — `public_access_cidrs` tightening tracked separately.

#### e) `aws_security_group.eks_nodes` description coverage

Top-level `description` plus per-rule descriptions for:
- Node-to-node intra-cluster TCP (self ingress, ports 0–65535).
- Control-plane → kubelet/extension API (1025–65535).
- Control-plane → node webhook/HTTPS (443).
- Outbound `0.0.0.0/0` (annotated `tfsec:ignore:aws-ec2-no-public-egress-sgr` — nodes need NAT-routed egress for image pulls and AWS APIs).

### 6. MODIFIED: `tf/rds.tf` — SG descriptions + suppressions with rationale

- `aws_security_group.rds` gained top-level + per-rule descriptions; egress annotated `tfsec:ignore:aws-ec2-no-public-egress-sgr` (RDS managed-network egress for AWS service calls; default 0.0.0.0/0 retained for parity with provider defaults — `lifecycle.ignore_changes` handles drift).
- `aws_secretsmanager_secret.rds_credentials` annotated `tfsec:ignore:aws-ssm-secret-use-customer-key` — using AWS-managed KMS today; CMK rollout tracked separately.
- `aws_rds_cluster.main` annotated `tfsec:ignore:aws-rds-encrypt-cluster-storage-data` — using default AWS-managed KMS key.
- `aws_rds_cluster_instance.main` annotated `tfsec:ignore:aws-rds-enable-performance-insights-encryption` — Performance Insights uses default AWS-managed key.

### 7. MODIFIED: `tf/opensearch.tf` — SG descriptions

`aws_security_group.opensearch` gained top-level + per-rule descriptions:
- `description = "Security group for dify-${var.deployment_id} OpenSearch domain"`
- Ingress 443 from EKS — `"HTTPS to OpenSearch from EKS worker nodes"`.
- Ingress 9200 from EKS — `"OpenSearch REST API from EKS worker nodes"`.
- Egress 0.0.0.0/0 — `"Allow all outbound traffic"`, annotated `tfsec:ignore:aws-ec2-no-public-egress-sgr` (OpenSearch ENIs need outbound for snapshots / KMS).

### 8. MODIFIED: `tf/s3.tf` — suppressions with rationale

- `aws_s3_bucket.dify_storage` annotated `tfsec:ignore:aws-s3-enable-bucket-logging` — access logging is opt-in via central log bucket.
- `aws_s3_bucket_server_side_encryption_configuration.dify_storage` annotated `tfsec:ignore:aws-s3-encryption-customer-key` — using SSE-S3; CMK migration tracked separately.

### 9. MODIFIED: `tf/ecr.tf` — suppressions with rationale

Both `aws_ecr_repository.dify` and `aws_ecr_repository.dify_ee_plugin` annotated:
- `tfsec:ignore:aws-ecr-enforce-immutable-repository` — application/plugin image flow re-uses tags during dev/test cycles and plugin install/update.
- `tfsec:ignore:aws-ecr-repository-customer-key` — using AWS-managed encryption (AES256); CMK migration tracked separately.

### 10. MODIFIED: `tf/irsa.tf` — IAM scope rationale

- `aws_iam_policy.dify_ee_s3_policy` annotated `trivy:ignore:AVD-AWS-0345` — broad object actions (Get/Put/Delete/List/multipart) are required for app uploads, plugin assets, and lifecycle ops; resource scope is restricted to objects under the Dify-owned storage bucket.
- `aws_iam_policy.s3_access` annotated `tfsec:ignore:aws-iam-no-policy-wildcards` — wildcard scoped to `dify_storage` bucket prefix only.

### 11. MODIFIED: `tf/vpc.tf` — public-subnet auto-assign off, VPC Flow Logs note

- `aws_subnet.public.map_public_ip_on_launch` flipped from `true` to `false`. The internet-facing ALB and NAT gateway do not rely on auto-assigned public IPs, so any EC2 placed in a public subnet by accident no longer becomes immediately reachable from the internet.
- `aws_vpc.main` annotated `tfsec:ignore:aws-ec2-require-vpc-flow-logs-for-all-vpcs` — VPC Flow Logs not provisioned here; enable via central logging stack if required.

### 12. MODIFIED: `scripts/2_verify_tf_deployment.sh` — Redis verification handles TLS endpoint format

```bash
# Derive replication group ID from deployment_id. The Redis endpoint starts
# with "master." (or "configuration.") when transit encryption is enabled,
# so cutting on the first dot does not give the replication group id.
local replication_group_id="dify-${DEPLOYMENT_ID}-redis"
```

Previously the script extracted the replication group ID by taking the first dot-segment of `REDIS_ENDPOINT`. With transit encryption enabled, ElastiCache returns `master.dify-<id>-redis.<rest>` (or `configuration.<...>` on cluster mode), which broke that extraction. Switched to deriving from `DEPLOYMENT_ID`.

### 13. MODIFIED: `scripts/3_post_tf_apply.sh` — surface password key into config_*.env

Reads the new `password_encryption_key` Terraform output and writes:

```
PASSWORD_ENCRYPTION_KEY=<base64>
```

…into the generated `secret/config_*.env` file.

### 14. MODIFIED: `scripts/4_generate_dify_helm.sh` — TLS-aware Redis + key substitution

Three changes:

#### a) Newest-first env-file ordering

```bash
done < <(find "$SECRET_DIR" -maxdepth 1 -name "*.env" -type f -print0 | sort -zr)
```

`show_menu` defaults to index 0 when stdin is not a TTY. Sorting newest-first prevents a stale `config_*.env` from a pre-TLS deploy (different `REDIS_ENDPOINT` format) from leaking into `values.yaml`.

#### b) Password-encryption-key substitution

```bash
if [ -z "${PASSWORD_ENCRYPTION_KEY:-}" ]; then
    PASSWORD_ENCRYPTION_KEY=$(openssl rand -base64 32)
    log_warning "PASSWORD_ENCRYPTION_KEY was not set in the sourced config.env."
    ...
fi
sed -i.bak "s|{{password_encryption_key}}|${PASSWORD_ENCRYPTION_KEY}|g" "$temp_file"
```

The `openssl rand` path is now a *fallback only* — it warns loudly that the database may already contain ciphertext encrypted with a different key.

#### c) `S3_ENDPOINT` removed from substitution

`{{s3_endpoint}}` no longer expanded in templates. The Helm chart's `s3.endpoint` is intentionally set to `""` so kaniko's `S3_ENDPOINT` env does not misroute STS `AssumeRoleWithWebIdentity`.

### 15. MODIFIED: `scripts/helm_templates/values.example.{prod,test,quick-poc}.yaml`

- `externalRedis.useSSL: true` — matches the TF-side TLS-only Redis.
- `enterprise.passwordEncryptionKey: {{password_encryption_key}}` — sourced from TF output, not regenerated by the script.
- `plugin_daemon` ServiceAccount now binds to `dify-api-sa` so plugin-daemon pods inherit the S3 IRSA role and can write plugin assets to the storage bucket.

### 16. NEW: `.github/workflows/security.yml`

Adds a CI job that runs:
- **gitleaks 8.30.1** — secret-scanning across the working tree and history (allowlist in `.gitleaksignore`).
- **trivy** — IaC and config scanning across `cloud/aws/tf/` (replaces the earlier tfsec usage).

The workflow runs on every push and PR.

### 17. NEW: `.gitleaksignore`

Allowlist for known false positives:
- Redacted `innerApiKey` samples in template files.
- Pre-existing matches in git history that have already been remediated.

## Net Behavioural Changes for New Deploys

| Area | Before PR7 | After PR7 |
|------|------------|-----------|
| Redis client URL | `redis://...` | `rediss://...` (TLS-only) |
| Redis at-rest encryption | off | on |
| `enterprise.passwordEncryptionKey` | regenerated by `openssl rand` on every helm regen | TF-managed (`random_bytes`), stable across applies |
| Public subnet auto-public-IP | on | off |
| EKS Kubernetes secrets | not envelope-encrypted | KMS-envelope-encrypted (CMK with rotation) |
| EKS control-plane logs | not enabled in TF | api/audit/authenticator/controllerManager/scheduler |
| Worker IMDS | v1 + v2 | v2 required |
| SG / SG-rule descriptions | absent | present on every resource and rule |
| CI security scanning | none | gitleaks 8.30.1 + trivy on every push/PR |
