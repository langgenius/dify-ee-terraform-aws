# Contributing

Thanks for your interest in improving the AWS deployment of **Dify Enterprise Edition**. This repository ships the Terraform stack and helper scripts that provision a production-ready EKS environment for Dify on AWS (both standard and China regions). Contributions of every size are welcome — from typo fixes to new region support.

This guide covers what you need to know before opening a pull request. The community also adheres to the [LangGenius Code of Conduct](https://github.com/langgenius/.github/blob/main/CODE_OF_CONDUCT.md).

## Before you jump in

Looking for somewhere to start? Browse the [open issues](https://github.com/langgenius/dify-ee-terraform-aws/issues), especially anything labeled `good first issue` or `help wanted`.

If you're planning a non-trivial change (new resource type, schema-breaking variable rename, region support, etc.), please open an issue first to discuss the design before writing code. Small fixes (typos, docs, obvious bugs) can go straight to a PR.

### Bug reports

Please include:

- A clear, descriptive title
- The exact `terraform` / AWS CLI / kubectl / helm versions you're using
- AWS region and whether you're using a standard partition or `aws-cn`
- The relevant block from your `terraform.tfvars` (with secrets redacted)
- The full error output (sanitize ARNs and account IDs if needed)
- Steps to reproduce and the expected behavior

Triage priority:

| Issue type | Priority |
| --- | --- |
| Broken `terraform apply` on a clean environment, security issues, IRSA/IAM misconfiguration | Critical |
| Region-specific failures, drift between docs and code, performance regressions | Medium |
| Cosmetic, naming, log-message tweaks | Low |

### Feature requests

Please include:

- A clear use case (what AWS scenario does this unlock?)
- Whether the change should be opt-in (new variable with safe default) or default behavior
- Any compatibility considerations for existing deployments and for AWS China region

## Submitting your PR

### Pull request process

1. Fork the repo and create a feature branch off `main`. Branch naming follows `feat/...`, `fix/...`, `chore/...`, `docs/...`.
2. Make your changes. Keep PRs focused — one logical change per PR.
3. Run the local checks listed below.
4. Commit using the [Conventional Commits](https://www.conventionalcommits.org/) style (e.g. `feat: support arm64 node groups in cn-northwest-1`). This matches the existing history.
5. Push and open a PR against `main`. Link the related issue (`closes #123`).
6. A maintainer will review. Address feedback by pushing additional commits to the same branch — please don't force-push during review unless asked.

### Local checks

Before pushing, please run from `cloud/aws/tf/`:

```bash
terraform fmt -recursive          # Format .tf files
terraform validate                # Catch obvious schema errors
terraform plan -out=tfplan        # Verify the plan against your sandbox account
```

For shell scripts under `scripts/aws/` and `cloud/aws/scripts/`:

```bash
shellcheck scripts/aws/**/*.sh cloud/aws/scripts/*.sh
```

### Things we will reject

- **Anything containing real AWS account IDs, ARNs, access keys, RDS passwords, tfstate, or unredacted tfplans.** Our `.gitignore` covers the common cases (`*.tfstate*`, `*.tfvars`, `secret/`, `tfplan`); double-check before pushing. If you accidentally commit a secret, **rotate it immediately** and tell us — we'll help purge it.
- Changes that break AWS China region (`aws-cn` partition) without a clear opt-out.
- Hardcoded region/AZ/account values that should be variables.
- New resources without corresponding outputs and documentation.
- Pinning provider versions backwards without justification.

### AI-assisted contributions

We welcome contributions written with the help of AI coding assistants (Claude Code, Cursor, Copilot, etc.). To keep the work reviewable and reproducible, **if a meaningful portion of the change was generated by AI, please include the assistant's plan and implementation notes** alongside the code.

- Place them under a dated changelog folder: `cloud/aws/changelog-YYYY-MM-DD-<short-topic>/`
- Filenames must start with `PLAN:` (the design or task breakdown the AI worked from) and `DOC:` (the implementation notes, decisions, and any deviations from the plan). Both `.md` files are required for non-trivial AI-assisted PRs.
- Example: `cloud/aws/changelog-2026-04-20-add-graviton-support/PLAN:GRAVITON_NODE_GROUPS.md` and `DOC:GRAVITON_NODE_GROUPS.md`
- See `cloud/aws/changelog-2026-01-28-add-HPA-and-CA/` for the existing format.

Trivial AI-assisted changes (typo fixes, single-line tweaks, doc rewording) do not need plan/doc files.

### Documentation

If your change affects user-visible behavior, please update the relevant docs in the same PR:

- `cloud/aws/README.md` — main deployment guide
- `cloud/aws/CLAUDE.md` — architecture and configuration reference
- `cloud/aws/tf/terraform.tfvars.example` — variable documentation
- The relevant changelog folder under `cloud/aws/changelog-*/` if introducing a major feature

## Local development setup

You'll need:

- Terraform >= 1.5
- AWS CLI v2, configured with credentials that can create EKS, RDS, ElastiCache, OpenSearch, S3, ECR, and IAM resources
- `kubectl` and `helm` v3
- A throwaway AWS account or sandbox — please do **not** test against shared production accounts

Read [`cloud/aws/README.md`](cloud/aws/README.md) for the full deployment walkthrough and [`cloud/aws/CLAUDE.md`](cloud/aws/CLAUDE.md) for the architecture overview.

## Security disclosures

Please **do not** open public issues for security vulnerabilities. Instead, email security@dify.ai with details. We'll acknowledge within two business days and coordinate a fix.
